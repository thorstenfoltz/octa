# Chatbot (in-GUI assistant)

A docked chat panel (`src/app/chat_panel/`, a dir-module: `mod.rs` = panel shell + body/header/messages/input; `controls.rs` = profile/Ollama/context-chip row; `windows.rs` = prompts + history windows; `session.rs` = session lifecycle + `send_chat_message`; `context.rs` = `build_tool_context` + edit drain; `helpers.rs` = render/format free fns. App-level like SQL) where an LLM drives Octa's tools in an agentic loop over the open tabs/files. Toggle via toolbar **Analyse -> Assistant**, **View** menu, or `ShortcutAction::ToggleChatPanel` (default `Ctrl+Shift+A`); header has a close [x]. GUI-only. The input row's `@`-mention autocomplete consumes Up/Down/Enter/Tab keys **before** the multiline `TextEdit` renders (mirrors the SQL editor; the editor would otherwise eat them) — Enter accepts a suggestion while the popup is open, sends otherwise. **Saved prompts**: `src/app/chat_prompts.rs` (`ChatPrompt`, `<config_dir>/chat_prompts.json`), `OctaApp.chat_prompts` + `chat_prompt_save: Option<ChatPromptDraft>`, naming dialog `src/app/dialogs/chat_prompt.rs`. **Prompts** button opens a manager **window** (`render_prompts_window`, standard `DialogSize` chrome via `ChatPanelState.prompts_window_open`/`prompts_window_size`): save-current / Insert / delete. The chat **History** window also uses the standard chrome now (`session_list_size`). i18n `chat.prompt_*`/`chat.prompts_hint` + `dialog.prompt_*`.

Core reuse lever: each MCP tool's work lives in `pub fn run(ctx: &ToolContext, p: &Params) -> anyhow::Result<Value>` (`src/mcp/tools/<name>.rs`); the MCP `handle` is a thin `server.tool_context()` -> `spawn_blocking(run)` wrapper, and the chat layer calls the **same** `run`. `ToolContext`/`Source`/`TableSnapshot`/`source_from` live in `src/mcp/tools/mod.rs`; `resolve(&Source)` reads via `read_with_registry` or clones an open-tab snapshot. Single-source tools' `Params` carry `open_tab: Option<String>` (`"@active"`, a tab name, or absent->`path`); compare/diff carry `open_tab_a`/`open_tab_b`; `write_table`/`edit_table` reject an `open_tab` target. `path` fields are `#[serde(default)]`.

**The export folder is a default, not a fence (user, 2026-11-04: "that's freedom").** With writes on, `allow_existing_writes` lets an absolute path go anywhere; the prompt and docs must not say writes are confined. **Filesystem sandbox (chat only).** `ToolContext` carries `restrict_filesystem` + `allowed_read_paths` (canonical open-tab paths) + `export_dir`; `for_mcp` leaves them off. `build_tool_context` (`chat_panel/context.rs`) sets them for chat: reads confined to open tabs (`ensure_readable`); a multi-table file is fully reachable once any sheet is open. Writes go through `resolve_write_path` (bare name -> `export_dir`; absolute path honoured). `TableSnapshot.handle` (`#1`...) addresses same-named tabs; `snapshot_for_pathish(s)` matches handle/name/filename (gated on `table.is_none()` so sibling-sheet reads still hit disk). `run_sql.extra_tables` resolve open tabs (`add_table` + `TableOrigin::TabClone`); `run_sql.write_to` also writes plain file formats. Chat-only tool `create_chart` (`src/mcp/tools/create_chart.rs`, in `define_chat_tools!`, no MCP `handle`) reuses `octa::data::chart::build_chart` + `chart_export`.

**Non-tabular files.** Text/code/Markdown files load as a single `Line` column. Chat-only tools `read_text` (joins the `Line` column into the file's text — captures in-memory edits) and `write_text` (writes content to a new file in `export_dir`, an absolute path, or back to an open tab's file on disk via `open_tab`; the live editor does **not** refresh — the user reloads). Both live in `src/mcp/tools/{read_text,write_text}.rs` (no MCP `handle`). The system prompt (`src/app/chat/mod.rs::build_system_prompt`) tells the model to use these for prose/code.

Module layout under `src/app/chat/`:
- `types.rs` - `Role` / `ContentBlock {Text|ToolUse|ToolResult}` / `Message` / `ChatEvent` / `StopReason` / `ToolDef`.
- `tools.rs` - `define_chat_tools!` builds **both** `tool_defs()` (schemas from `schemars::schema_for!(Params)`, `$schema`/`title` stripped) and `dispatch(ctx, name, args)` from one list. Descriptions come from a `pub const DESCRIPTION` per tool module. **Not all of them are sent.** All 62 definitions are ~99 KB / ~33k tokens *per request*, and the agent loop re-sends them every round, so `initial_tool_defs(allow_writes, disabled)` sends the **core** group (~6.5k) plus one meta-tool, `ENABLE_TOOLS` (`enable_tools`), whose description names the remaining tools by group without their schemas. `enable_tools_def` builds that menu (returns `None` when nothing is left to fetch, so an empty menu is never advertised) and `enable_groups(args, allow_writes, disabled, already)` answers a call with the definitions to append. `tool_defs_for(allow_writes, disabled)` is the full pool both draw from: minus `WRITE_TOOL_NAMES` when the profile is read-only, minus `AppSettings.chat_disabled_tools`.
- `tool_groups.rs` - the catalogue: every tool's `ToolGroup` (Core / Quality / Compare / Combine / Reshape / Databases / Cloud / Write) and a one-line English `when` for the settings tooltip, plus `approx_tokens` (bytes of description + schema / 3). `every_tool_is_catalogued` pins it against `define_chat_tools!`; `the_core_payload_stays_small` fails if the first request grows past 10k tokens or stops being less than half the full set. `publish_to_settings()` (called once from `main.rs` before any UI) hands the list to `octa::ui::settings::chat_tools`, the library-side registry the Settings list reads - the tools live in the binary and the dialog in the library, so that `OnceLock` is the seam.
- `providers/` - one file per backend (`anthropic`, `openai`, `openai_compat`/`ollama`, `gemini`) behind `trait ChatProvider`. **OpenAI proper streams via the Responses API** (`openai_responses.rs`, `/v1/responses`): gpt-5.x 400s on `reasoning_effort` + function tools at chat/completions. `build_responses_body` sends `store:false` + (with reasoning) `include:["reasoning.encrypted_content"]`, FLAT tools `{type:"function",name,...,strict:false}` (strict must be explicit false - Responses defaults it on and schemars schemas do not satisfy it), `instructions` = system, `max_output_tokens`; reasoning = effort **word** (numeric -> local error), temperature OMITTED while reasoning is set. Reasoning items stream back as `ChatEvent::ProviderData` -> `ContentBlock::ProviderData{provider,data}` and are replayed verbatim before their turn's `function_call` items (gpt-5.x rejects a replayed function_call without its paired reasoning item); other providers' wire mappers filter the variant out. `handle_event` is a pure per-SSE-event fn (no `[DONE]`; `response.output_item.done` carries complete function_call arguments so argument deltas are ignored). `agent.rs` accumulates an ordered `raw_blocks: Vec<ContentBlock>`; dispatch iterates ToolUse only. `openai.rs` keeps the chat/completions helpers for `openai_compat`. **`ollama.rs` is native `/api/chat`, not OpenAI-compatible**, and the reason is `num_ctx`: Ollama sizes its default context from VRAM (4k on a modest box) while Octa's first request is ~6.5k tokens of tool schemas, so it drops the oldest non-system message to fit - the user's question - and Qwen 3.8 then answers `500 no user query found in messages` while every other model silently answers a question it cannot see. `num_ctx` has no field in Ollama's `ChatCompletionRequest` and unknown keys are dropped, so the native endpoint is the only way to raise the window per request. It streams **newline-delimited JSON**, hence `stream_lines` (the shared POST + line loop `stream_sse` now wraps); `handle_line` is a pure per-line fn so the wire format is testable without a server. Differences from the OpenAI mapping, all in `messages_to_wire`: `arguments` is an object not a string, assistant `content` is a plain string never null, and a tool result carries `tool_name` beside `tool_call_id` (renderers key off the name). `done_reason` is `stop` even for a tool turn, so `StopReason::ToolUse` comes from having seen a call. The final line's `eval_count`/`eval_duration` become `ChatEvent::Throughput` (tokens/s, shown after the usage meter; `ChatSessionState.tokens_per_second`, last turn only, Ollama is the only provider that measures it - a wall clock in the agent would miss thinking it never sees). The same line's `prompt_eval_count`/`prompt_eval_duration` become `ChatEvent::PromptSpeed` -> `ChatSessionState.prompt_read` (shown in the meter's hover as `chat.usage_read`: it explains the silent minutes before the first token), and `StreamingTurn.started` feeds the spinner clock (restarts per phase; `request_repaint_after(1s)` while streaming). `stream_lines` takes the response-header timeout per call: hosted APIs 120s (`HOSTED_RESPONSE_TIMEOUT`, an Ask box has no cancel), Ollama 30 min (`ollama::RESPONSE_TIMEOUT`) because it sends no bytes until model load + full prompt eval are done, and the hosted cut produced `timeout: receive response` on Explain. Do NOT "simplify" it back onto `run_openai`. `ProviderConfig.max_tokens: Option<usize>` (None=omit), from `chat_profiles::max_tokens_for`: `ChatModelProfile.unlimited_tokens` (user, 2026-11-04: the model itself is the limit) or the global `chat_max_tokens_unlimited`. On Ollama None also takes the model's own window (`ollama::context_length`, `/api/show`, cached per model) instead of `NUM_CTX`. Hints name no model versions (user: they change too often). Anthropic is the exception that *requires* the field, so `anthropic::resolve_max_tokens` turns None into the model's own ceiling, read once per model from `GET /v1/models/{id}` and cached in `MODEL_CAPS` (128k on the Claude 5 generation, 64k on Haiku 4.5), falling back to `FALLBACK_MAX_TOKENS` = 16,384 when the lookup fails. **Do not put that ceiling in a table here**: it was a flat 16,384 for exactly that reason and quietly cost users 87% of a long answer; a table is wrong the day a model ships. `gemini.rs::to_gemini_schema` sanitises schemars JSON Schema to Gemini's OpenAPI subset (resolve `$ref`, `Option`/`anyOf`->`nullable`, drop `additionalProperties`/`$schema`/`$defs`/`default`/`title`) else Gemini 400s. `stream_sse` extracts `error.message` from non-2xx bodies. Ollama is first-class: keyless `ChatProviderKind::Ollama`, `chat_ollama_url`, `src/app/chat/ollama.rs` (`is_running`/`list_models` via `/api/tags`; `start_server` spawns `ollama serve` in its own process group via std `CommandExt::process_group(0)` (pgid = pid) so `stop_child_group` kills server + `llama-server` child with `libc::kill(-pgid)`; needs the `libc` unix dep for that kill). Panel worker threads do the model dropdown + Refresh/Start/Stop + ~5s status poll; Octa-started server killed on `on_exit`. SSE over blocking `ureq` on a `std::thread`; `stream_lines` uses `into_reader()` (not `read_to_string`, which defeats streaming) and `stream_sse` is the `data:`-stripping wrapper over it. Providers assemble tool calls fully before emitting `ChatEvent::ToolCall`.
- `session.rs` - `ChatSessionState` (messages, `streaming`, `running`/`cancel` `Arc<AtomicBool>`, error) behind `Arc<Mutex<..>>`.
- `agent.rs` - `spawn_turn` runs on a `std::thread` holding only a cloned `egui::Context` + `Arc<Mutex<state>>` + a moved `ToolContext` (never borrows `TabState`). Loops up to `chat_max_tool_iterations`: stream -> commit -> dispatch tool calls (capped by `truncate_for_model`, 100 KB) -> append -> repeat. `tools` is **mutable**: an `enable_tools` call is answered in the loop (not in `dispatch`, which cannot reach the turn's tool list) and its groups are appended for the rest of the turn. A round that only fetched tools does **not** spend an iteration - with the default of 3 one fetch would eat a third of the budget - bounded by `max_fetch_rounds` (= the number of groups) so a model that only ever fetches still terminates. A call to a tool that is not in the live list is refused with a message saying whether it is switched off in Settings or simply not loaded yet. Per-turn `cancel`/`running` are fresh `Arc`s installed by `send_chat_message`; `cancel_chat` flips cancel and clears state; the worker's finally only clears shared state when `Arc::ptr_eq` confirms it's still the active turn.
- **A model is not a witness (user report 2026-11-04: the same error 4 times, then "I've added a new column").** `agent.rs` ends the turn after `MAX_SAME_FAILURES` (3) of one tool failing with one error, with `chat.tool_stuck`, before the model can answer; a reply right after a failed round gets `chat.last_tool_failed`. `run_typed` puts the tool's schema in an "invalid arguments" error. `edit_open_tab` only queues, so it checks `TableSnapshot.read_only` (`OctaApp::tab_is_readonly`) first, or it reports success for an edit the drain then drops. Its DESCRIPTION spells out the `op` shape: `gemma4` guessed `action` from the old prose.
- **A database tab is not its table, and it is never fetched (user, 2026-11-04: "what if I have millions of rows in Databricks"; same rule as the GUI's pushdown, decided 2026-10-01: SQL on the server, no download, fallback = loaded rows + a note).** Such a tab's `total_rows` is a "more may exist" flag equal to the loaded count, so `is_partial` says no. `build_tool_context` sets `TableSnapshot.db: Option<SnapshotDb>` when `db_origin` and `source_has_more()`; its `source` is `pushdown::server_source_for` (setting on, not SQLite, connection saved, server filter and hash columns carried), `None` with unsaved edits, since the server's rows would make an edit vanish. `ToolContext::db_tab(source)` is the door. **Server path:** `run_sql` (`server_statement`: the query verbatim with `data` and any `extra_tables` on the same connection as CTEs, merged into a leading WITH, in the server's own SQL, always read-only via `ensure_write_allowed` on an `allow_writes: false` copy; `write_to` writes the whole result up to the load cap through the normal path, with `SELECT * FROM data`), `count_rows`, `profile` (`pushdown::summary`, one scan: median, quartiles and mode left out, a statement per column each), `value_frequency`, `sample` (Fast), `read_table` (`view::page_sql`, sorts on the server, natural order stays local), `correlation`, `pivot` (not unpivot), `resample_timeseries` and `rolling_window` (a date held as text and a sum over times stay local, as in the GUI), `quality_report` (per-column counts on the server, value patterns from the loaded rows, named in `from_loaded_rows`), `schema` (from the tab). **Everything else** gets the loaded rows from `resolve_snapshot`, which leaves `ToolContext.loaded_rows_note`; `dispatch` puts it on the result, because most tools build their own JSON. A failed server read is an error, never a silent fallback. `edit_open_tab` stays on the loaded rows and says so. **Never add a tool path that fetches the table**, and `limit: 0` / `unlimited` do not mean it here. A SELECT's result is cut too: `tools::query_for_response` (also `query_db`) reads `row_cap + 1` under `formats::ThreadRowCap`, a per-thread cap, because `InitialLoadRowsGuard` is one number for the process and the GUI may be loading a file; every connector reads the cap on the calling thread when `query` starts. Tests `mcp/tools/mod_db_tab_tests.rs`, a DuckDB file as the server, `FETCH_LIMIT` proves nothing was fetched and `the_fetch_limit_bites_on_this_server` proves that proof; every engine's statement goes through the gate there too. `mod_db_tab_live_tests.rs` runs all of it through `dispatch` per `OCTA_TEST_*_URL` (Postgres, MySQL/MariaDB, SQL Server, ClickHouse, Trino with host `http://...`, Oracle; run by hand, CI's db-live job does not run bin tests). **Databricks has no entry and must not get one (user, 2026-11-04: never on their connection)**: its statements were run once on `apache/spark:3.5.3` with `spark.sql.ansi.enabled=true` through a throwaway connector over beeline. Snowflake, BigQuery, Redshift, Exasol and Athena were never run on a server; measured once on Postgres with 5M rows / 403 MB: peak 126 MB, count 0.1 s, GROUP BY 0.2 s, profile 12 s.
- **Debug box** (`chat_panel/trace.rs`, `ChatPanelState.show_trace`, off at every start): `agent.rs` records one `TraceStep` per request (`begin_trace_step`, `trace_step`: system prompt, tool names, messages new since the last step via `trace_seen`, reply, per-step tokens and time, `TraceToolRun`s, error) whether the box is open or not, so it can be ticked after the fact. `ChatSessionState.trace`, capped at 200 steps, never persisted. The Ask boxes are not traced. It costs no tokens: nothing from it reaches a request. `AppSettings.chat_export_trace` (off by default, user 2026-11-05) adds the steps to an export, uncut: `export::trace_to_markdown`, and a `trace` field beside the session in `export::to_json`, which with no steps is byte-identical to the plain session.
- `persist.rs` - one pretty JSON per session under `<config_dir>/chat_sessions/`; autosaved per turn (debounced) and on new/load.
- `audit.rs` - opt-in tool-call audit log (`chat_audit_log_enabled`, off by default): each tool call appends one JSON line (`AuditEntry`: tool, args/result bytes, duration, is_error, ts) to `<config_dir>/chat_audit/<session_id>.jsonl`. `TurnRequest.audit_session: Option<String>` (set in `send_chat_message` from the session id when enabled) gates recording in `agent.rs`'s dispatch loop. Startup size warning: `OctaApp::new` sums `audit::total_size_bytes()`, sets `status_message` when `> chat_audit_log_warn_bytes` (default 10 MB) and `chat_audit_log_warn_enabled`. i18n `chat.audit_*`, `settings_hint.chat_audit_*`.
- `secrets` - in the library at `src/ui/settings/secrets.rs` (re-exported `crate::app::chat::secrets`). Per-provider keys, precedence **env -> keyring -> plaintext settings.toml**; `set_api_key` reports keyring-vs-fallback, `storage_location` reports the source. **Linux keyring = freedesktop Secret Service**, pure-Rust zbus. `keyring = "4"` is a single plain dep (no per-OS `[target.'cfg(..)']` blocks): its default `v1` feature picks `zbus-secret-service-keyring-store` on Linux (declared upstream with `crypto-rust`, so no libdbus and no OpenSSL), `apple-native` on macOS and `windows-native` on Windows, and `v1::Entry::new` registers the store itself on first call.

**Model profiles** (`src/ui/settings/chat_profiles.rs`, library-side since `AppSettings` is): `ChatModelProfile { id, name, description, kind, model, temperature, reasoning, verbosity, pro_mode, base_url, use_own_key, allow_writes }` - an arbitrary `Vec` of named provider+model+params setups, several per provider allowed. **`allow_writes` (default false) REPLACES the global `write_protection` for the chat surface** (that switch keeps governing GUI file saves + the MCP startup default): `send_chat_message` passes it into `build_tool_context` (`allow_existing_writes`/`allow_schema_changes`/`read_only: !allow`) and `tools::tool_defs_for(allow, disabled)` (filters `WRITE_TOOL_NAMES` out of the advertised list; `dispatch` also refuses them on a `read_only` ctx, and `run_sql write_to` gates itself - that also closed the `--mcp-read-only` hole). The legacy-migration seed inherits `!write_protection`; profiles created later default read-only. The edit drain gate is `is_readonly() || !active_profile(..).allow_writes`. The panel shows the answer beside the profile picker as **Writes on / off** (`OctaApp::writes_status_keys`, user 2026-11-05), read from `assistant_may_write`, the check a reply runs under, so F8 and the modes without tools read off too. `build_system_prompt(tab_summaries, allow_writes, has_tool_menu)` adds a line telling the model that more tools exist behind `enable_tools` (only when the menu is actually sent), and swaps the write-tool guidance for an explicit READ-ONLY paragraph when writes are off (else the model speculates about "missing tool bindings" instead of naming the profile switch). `AppSettings.chat_profiles` + `chat_active_profile` (the id). `ensure_profiles(&mut settings)` runs in `AppSettings::load` (wrapping `load_raw`, so *every* path incl. parse-failure gets one) and on Settings-apply: seeds one profile from the legacy `chat_provider`/`chat_models`/`chat_temperature`/`chat_base_url`/`chat_ollama_url` fields (which stay as migration source + fallback) and re-points a dangling active id. `active_profile(&settings)` is the accessor. `id` is minted once via `fresh_id` and frozen (it names the keyring entry). Panel header = one profile dropdown (+ **Profiles...** -> Settings); Ollama keeps its server controls + discovered-model list in the panel, writing the pick back into the active profile (`set_active_profile_model`). The **Ollama server URL stays global** (the probe/start/stop target); a profile's `base_url` overrides it per request. **The limits belong to the model (user, 2026-11-12)**: `ChatModelProfile.{max_tokens, max_tool_iterations, result_row_limit}` (`Option<usize>`) and `export_dir` (String), plus `unlimited_rows` beside `unlimited_tokens`, each empty = the general `chat_*` setting (tool rounds, general and per profile, go up to `MAX_TOOL_ITERATIONS` = 1000, never unlimited; the default stays 3), which stays as the default; resolve only through `chat_profiles::{max_tokens_for, max_tool_iterations_for, result_row_limit_for, export_dir_for}`. The form shows the general value as the field's hint text. File > Report... keeps the general export folder. Temperature is greyed on a `cli_program()` profile (`greyed.subscription_no_temperature`). The `write_protection` switch is labelled **Refuse column changes in database files** and sits under Settings > Databases since the same day (TOML key unchanged); it never governed the Assistant.

**Prompt caching (Anthropic)**: `build_body` sends `system` as a one-element block array carrying `cache_control: ephemeral`, and puts a second marker on the last message's last block. Anthropic hashes the prefix in the order tools -> system -> messages, so the marker on `system` covers the whole tool payload (the part that repeats unchanged every round) and the rolling one covers the conversation. Two of the allowed four. `message_start` is where the input token count comes from at all, and it sums `input_tokens` + `cache_creation_input_tokens` + `cache_read_input_tokens` so the meter keeps meaning "tokens sent". OpenAI and Gemini cache long prompts server-side with no request field, so nothing is sent for them.

**Thinking/reasoning**: `ProviderConfig.reasoning: Option<String>` (free text, empty = omit). One shared `parse_reasoning` turns the field into `Reasoning::Effort(word)` or `Reasoning::Budget(number)`, and each provider maps the two shapes onto the two knobs its API actually has - the *shape* picks the knob, so a level a provider adds later needs no release here. **Effort words are the current control everywhere**: OpenAI -> Responses `reasoning.effort` (`none`/`minimal`/`low`/`medium`/`high`/`xhigh`/`max`, which levels are legal is per model - GPT-6 Astra 400s on `none`; a number is a local error; temperature omitted while set); `anthropic.rs` -> `output_config.effort` (`low`..`max`, default per model: `medium` on Opus/Haiku 5.5, `high` on Fable 5.1 and Sonnet 5.5); `gemini.rs` -> `thinkingConfig.thinkingLevel`; compat -> `reasoning_effort` via the shared `build_body`, Ollama -> native `think`. **Numbers are the legacy path**, kept because older models still need them: `anthropic.rs` -> `thinking.budget_tokens` (min 1024, only Claude 4.5 and older; Opus 4.7 and later answer 400) and then forces `temperature: 1` + lifts `max_tokens`, both API requirements - `build_body` therefore returns `Result<Value, String>` and `stream_turn` `?`s it; `gemini.rs` -> `thinkingConfig.thinkingBudget` (Gemini 2.5 only, `0` off / `-1` dynamic; sending it alongside `thinkingLevel` is a 400). Ollama's native `think` takes a level or a bool and has no budget field at all, so `ollama::build_body` returns a local error for a number rather than letting the server reject it less legibly.

**Two more OpenAI-only knobs sit beside effort**, both free text/bool on the profile and rendered only for an OpenAI profile (`chat_section.rs`): `verbosity` -> `text.verbosity` (`low`/`medium`/`high`, its own top-level object, NOT part of `reasoning` - effort buys thinking, verbosity buys prose) and `pro_mode` -> `reasoning.mode: "pro"` (GPT-5.6 and GPT-6; others 400). `build_responses_body` assembles `reasoning` as a map so effort and mode can arrive independently, and **pro mode silences `temperature` exactly like an effort word does**, because it is still a reasoning request. Both are `#[serde(default)]`, so a settings.toml written before them parses unchanged.

**Temperature is `Option<f32>` because the current models reject the field itself**, not just a particular value. Blank in the profile form means `None` means the key never reaches the wire, and that is the only shape Claude Fable 5/5.1, Opus 4.7/4.8/5/5.5, Sonnet 5/5.5 and Haiku 5.5 accept (a non-default `temperature`, `top_p` or `top_k` is a 400 there on *every* request, thinking or not), and likewise OpenAI's reasoning models. Never "restore" a numeric default; the legacy migration's `Some(chat_temperature)` is for old profiles pointing at old models, and `seed_profile_from_legacy` sends it only when the install configured a model or changed the temperature (a fresh install lands on Haiku 5.5, which 400s on any temperature).

**Keys** (`src/ui/settings/secrets.rs`) are now **id-based**: `get_key_for/set_key_for/delete_key_for/key_storage_for(key_id, env_var, ..)`. Two id spaces: provider (`kind.id()`, shared by every profile of that provider, env-var backed) and profile (`profile_key_id(id)` = **`profile.<id>`** — namespaced so a profile named "Anthropic" can't clobber the shared `anthropic` key; no env var). `get_api_key`/`set_api_key`/... and `get_profile_key`/`set_profile_key`/... are thin wrappers. A profile resolves its key via `chat_panel::profile_api_key` (own key iff `use_own_key`, else shared).

Settings live in the **main Settings dialog** (`src/ui/settings/dialog/`, "Chat / Assistant" `CollapsingHeader`); the panel's Settings button opens it via `settings_dialog.focus_chat_section` (+ one-shot `focus_chat_profiles`). The big sections use nested sub-`CollapsingHeader`s to separate per-instance from global config: Chat = "Model profiles" / "Global options" (`chat_global_options_grid`) / "API keys" (`chat_api_keys_body`), Databases + Cloud = connection list up front (every Settings Edit/Remove list is a `control_row::button_list_grid`, whose text column wraps short of the buttons) with the add/edit form behind a sub-header titled `db|cloud.add_connection` or, while a row is being edited, `db|cloud.edit_connection`, `.open(Some(true))`-forced then (cloud also via one-shot `focus_cloud_form` from the sidebar "+ Add"). Save connection is the form's LAST row, under every field and (cloud) the secret it stores. **Writing mode** (2026-11-11, `chat/writing.rs` pure + `chat_panel/writing_ui.rs`): a fourth `ChatTurnMode::Writing` for text and code tabs (`raw_content` is `Some`). **One request, no tools**, like the other two non-Data modes, so the ordinary agent loop runs it; only the system prompt differs. The file's text (unsaved edits included) and the marked passage travel in the SYSTEM prompt, rebuilt each turn, so a follow-up sees the current text and the history never piles up copies of the file. The proposal is the WHOLE file between `~~~~~~octa-file` and `~~~~~~`: six tildes, because the file is often Markdown holding backtick blocks that would end a backtick fence early. A reply cut off before the closing line proposes nothing (`proposal_in`), and `with_ending_of` gives the proposal the file's CRLF and final line break. `send_chat_message` records `ChatPanelState.writing_sent` (tab id + the text sent); `collect_writing_offer` turns the finished reply into `writing_offer` before the transcript takes the session lock. The bar under the reply ALWAYS shows **Compare / Accept / Discard** (user, 2026-11-11: "I want always to be able to choose"); Compare puts the proposal into `compare_right_raw` and reuses the Text Diff view, remembering `shown_from` so every way out returns to that view, including the compare view's own close button (`writing_comparison_closed`, called from `central_panel/views.rs`, which also sends a text tab with no table to Raw instead of a blank Table view). Accept changes `raw_content` only, never the disk, and only while the tab still holds exactly the text the question was asked about (`chat.writing_stale` otherwise). `writing_blocked()` (Read-only mode or the profile's Allow writes off) greys Accept and is what `writes_status_keys` reads in this mode. **Undo change** is a bar button holding the before/after pair, because the Raw view's Ctrl+Z belongs to egui's text field and does not see text set from outside. `AppSettings.chat_writing_apply_directly` (off) applies the proposal the moment the reply is in, WITHOUT asking (user, same day); where `writing_blocked()` says no, the bar appears instead. Known ceiling: the whole file comes back, so long files cost output tokens; a patch format was left out on purpose.

**Subscription providers start the vendor's own program** (2026-11-11, `providers/cli.rs` + `claude_cli.rs` + `copilot_cli.rs` + `codex_cli.rs`): `ChatProviderKind::{ClaudeCli, CopilotCli, CodexCli}` (the Claude one is labelled **Anthropic (subscription)**, the user's wording 2026-11-11; id stays `claude_cli`), and `ChatProviderKind::cli_program()` is THE switch (`needs_api_key` is false for them, `default_model` and the preset lists are empty). **They do everything an API profile does (user, 2026-11-11: "subscriptions are cheaper, so users want that"), and Octa runs the tools, never the program.** `cli::flatten(system, messages, tools)` writes system prompt + `tools_prompt` (each tool's name, description, schema, and the block to call one with) + earlier turns (a `ToolUse` as that same block, a `ToolResult` as `[Result of <name>]`) into one text. The model asks for a tool with `~~~~~~octa-tool` / one JSON object `{"name", "arguments"}` / `~~~~~~` (six tildes like Writing's `octa-file`). `cli::Reply` shows prose as it arrives and holds back everything from the first opening line; `finish` turns the blocks into `ChatEvent::ToolCall` + `Done { ToolUse }`, so `agent.rs` is untouched and the same `dispatch`, sandbox, Allow writes, Read-only mode, `enable_tools` menu, trace and audit apply. A block that cannot be read (unclosed, not JSON, no name) is shown as text and ends the turn, never run; a turn that sent no tools looks for none. **Do not hand the program `octa --mcp` instead**: that second process sees files on disk, not open tabs or unsaved edits, and none of the chat gates. Ceiling: every tool round starts the program again with the whole conversation. `cli::run` starts the user's installed program in a fresh empty temp folder, writes the prompt to **stdin** (a whole file does not fit on a Windows command line), reads stdout line by line, kills the process group on cancel (`ollama::stop_child_group`), stops after `RUN_LIMIT` (30 min, the Ask boxes have no cancel) and reports the program's own stderr on failure; `cli::turn` wraps it (`parse: None` = the output is the answer, `Some(fn)` = one JSON event per line). The profile's `base_url` field doubles as the program path for these kinds (`config_for_profile`; never the global base URL). The Model dropdown is filled from the program (`ui/settings/cli_models.rs`: `codex debug models`, visibility `list`; `copilot help config`, the quoted names under `model`, plus `auto`; Claude has no listing, so `CLAUDE_ALIASES`), once per program on a worker. **Claude** (`claude -p --tools "" --strict-mcp-config --setting-sources "" --disable-slash-commands --no-session-persistence --system-prompt <one line> --output-format stream-json --include-partial-messages --verbose [--model m] [--effort e]`): **Anthropic confirmed to the user on 2026-11-11 that Octa may run on Claude subscriptions**, which lifted the earlier "we don't do Claude for now". ## Plain-language entry points

- **Plain-language filter ("Ask")**: the search bar's Ask toggle retargets the search box (placeholder, width, focus) and sends the sentence to a chat profile via `chat/ask_filter.rs` (**one request, no tools, no agent loop**, so a search box can never become an autonomous session). While Ask is on, typing does **not** filter, or a half-written question empties the table. The reply is parsed into `AskResult { predicates, values, sort }`; failures apply **nothing**. Needed one new filter type: `column_filters` is a value allow-set and cannot express `amount > 1000`, so `src/data/predicate_filter.rs` + `TabState.predicate_filters` evaluate comparisons in `recompute_filter`, delegating every comparison to `conditional_format::rule_matches` (one comparison engine). Applied conditions show as removable chips above the table. Worker + `ask_filter_job` slot drained in the update loop; status bar shows `search.ask_running`.
- **Plain-language query ("Ask SQL")**: the SQL panel header's Ask box, a direct sibling of the search bar's. `src/app/chat/ask_sql.rs` is pure (`build_prompt`/`parse_reply`/`splice_at`/`ask`) and **one request, no tools, no agent loop**, same reason. The answer is **spliced into the editor at the cursor** (`splice_at`, byte offset captured at Save time from `TextEdit::load_state`, clamped to a char boundary) and **never run** - the user reads it and presses Run. `parse_reply` refuses anything that is not a single SELECT: a quote-aware semicolon scan (`split_points_outside_literals`, `''` = escaped, so `'a;b'` stays data) allows one trailing `;` and nothing after it, and the leading verb must be SELECT or WITH. Every failure applies nothing rather than half a query. On a db-origin tab in server mode the prompt names the real `schema.table` and that engine's dialect (`DbEngine::label()`), else `data`/DuckDB. **That same case also grounds the model in the server's declared foreign keys**: `ask_sql_job` runs `db::relationships::scan` on the tab's schema through `db_conn_cache` (two catalog queries, no table data) inside the worker, and `ask_sql::related_tables_block` turns the result into prompt text - the tables one hop out, their column names, and the key pair each join uses, capped at 8 tables / 40 columns (token budget, not correctness). `build_prompt` takes it as a sixth argument and, when it is non-empty, swaps `- Refer to the table only as X` for four rules: exact names, **join only on a listed pair**, prefer the base table alone, and do not aggregate a base-table column through a join that multiplies rows (the fan-out trap). Gated three ways, each falling back to the old single-table prompt: server mode only (a local DuckDB query has no neighbours to join), a non-empty schema (`scan` addresses everything as `schema.table`), and `DbEngine::has_foreign_keys()` (`scan` reads every column *before* it discovers ClickHouse/Trino/Athena have no keys, so an ungated call sweeps the catalog for nothing on every question). A failed scan logs `tracing::warn!` and asks anyway. A cross-schema parent comes back without columns (the key query filters on the child's schema, the column query on its own) and is listed as `(columns not read)` rather than with an empty list that would invite invented names. Worker + `ask_sql_job` slot drained in the update loop, reusing `search.ask_running` for the spinner. **`ask()` takes the already-built prompt (5 args), not the table facts (8)** - eight trips `clippy::too_many_arguments` and the no-`#[allow]` rule forbids the escape hatch. `SqlViewContext.chat_profile_available` is how the view layer knows to grey the box without reading settings. **Ask never picks a table (user, 2026-11-04: "it chooses a table from the connection, that should not happen").** `sql_panel::ask_table_chosen` = the tab's own table where the query runs. Without it, `ask_sql::names_table` (last part of the name, whole word, any case) is the only way a table gets into the prompt: `server_tables_block` drops the unnamed ones and `schema_overview(max, wanted)` skips them before any `columns_of`. Listing them all with the rule "use only the tables above, else the closest query" is what forced the model to pick one. None named = the standalone prompt with placeholder names, in the server's dialect (`AskSqlFacts::no_schema`, decided on the worker, so the outcome carries the flag for the `ask_no_table_done` status). A failed catalogue read still refuses the question. i18n `sql.ask*` (6 keys).

Marked text in a chat bubble owns Ctrl+C, not the table underneath it: see the
"Who owns Ctrl+C" section in `.claude/rules/ui.md`.
