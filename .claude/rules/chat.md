# Chatbot (in-GUI assistant)

A docked chat panel (`src/app/chat_panel/`, a dir-module: `mod.rs` = panel shell + body/header/messages/input; `controls.rs` = profile/Ollama/context-chip row; `windows.rs` = prompts + history windows; `session.rs` = session lifecycle + `send_chat_message`; `context.rs` = `build_tool_context` + edit drain; `helpers.rs` = render/format free fns. App-level like SQL) where an LLM drives Octa's tools in an agentic loop over the open tabs/files. Toggle via toolbar **Analyse -> Assistant**, **View** menu, or `ShortcutAction::ToggleChatPanel` (default `Ctrl+Shift+A`); header has a close [x]. GUI-only. The input row's `@`-mention autocomplete consumes Up/Down/Enter/Tab keys **before** the multiline `TextEdit` renders (mirrors the SQL editor; the editor would otherwise eat them) — Enter accepts a suggestion while the popup is open, sends otherwise. **Saved prompts**: `src/app/chat_prompts.rs` (`ChatPrompt`, `<config_dir>/chat_prompts.json`), `OctaApp.chat_prompts` + `chat_prompt_save: Option<ChatPromptDraft>`, naming dialog `src/app/dialogs/chat_prompt.rs`. **Prompts** button opens a manager **window** (`render_prompts_window`, standard `DialogSize` chrome via `ChatPanelState.prompts_window_open`/`prompts_window_size`): save-current / Insert / delete. The chat **History** window also uses the standard chrome now (`session_list_size`). i18n `chat.prompt_*`/`chat.prompts_hint` + `dialog.prompt_*`.

Core reuse lever: each MCP tool's work lives in `pub fn run(ctx: &ToolContext, p: &Params) -> anyhow::Result<Value>` (`src/mcp/tools/<name>.rs`); the MCP `handle` is a thin `server.tool_context()` -> `spawn_blocking(run)` wrapper, and the chat layer calls the **same** `run`. `ToolContext`/`Source`/`TableSnapshot`/`source_from` live in `src/mcp/tools/mod.rs`; `resolve(&Source)` reads via `read_with_registry` or clones an open-tab snapshot. Single-source tools' `Params` carry `open_tab: Option<String>` (`"@active"`, a tab name, or absent->`path`); compare/diff carry `open_tab_a`/`open_tab_b`; `write_table`/`edit_table` reject an `open_tab` target. `path` fields are `#[serde(default)]`.

**Filesystem sandbox (chat only).** `ToolContext` carries `restrict_filesystem` + `allowed_read_paths` (canonical open-tab paths) + `export_dir`; `for_mcp` leaves them off. `build_tool_context` (`chat_panel/context.rs`) sets them for chat: reads confined to open tabs (`ensure_readable`); a multi-table file is fully reachable once any sheet is open. Writes go through `resolve_write_path` (bare name -> `export_dir`; absolute path honoured). `TableSnapshot.handle` (`#1`...) addresses same-named tabs; `snapshot_for_pathish(s)` matches handle/name/filename (gated on `table.is_none()` so sibling-sheet reads still hit disk). `run_sql.extra_tables` resolve open tabs (`add_table` + `TableOrigin::TabClone`); `run_sql.write_to` also writes plain file formats. Chat-only tool `create_chart` (`src/mcp/tools/create_chart.rs`, in `define_chat_tools!`, no MCP `handle`) reuses `octa::data::chart::build_chart` + `chart_export`.

**Non-tabular files.** Text/code/Markdown files load as a single `Line` column. Chat-only tools `read_text` (joins the `Line` column into the file's text — captures in-memory edits) and `write_text` (writes content to a new file in `export_dir`, an absolute path, or back to an open tab's file on disk via `open_tab`; the live editor does **not** refresh — the user reloads). Both live in `src/mcp/tools/{read_text,write_text}.rs` (no MCP `handle`). The system prompt (`src/app/chat/mod.rs::build_system_prompt`) tells the model to use these for prose/code.

Module layout under `src/app/chat/`:
- `types.rs` - `Role` / `ContentBlock {Text|ToolUse|ToolResult}` / `Message` / `ChatEvent` / `StopReason` / `ToolDef`.
- `tools.rs` - `define_chat_tools!` builds **both** `tool_defs()` (schemas from `schemars::schema_for!(Params)`, `$schema`/`title` stripped) and `dispatch(ctx, name, args)` from one list. Descriptions come from a `pub const DESCRIPTION` per tool module. **Not all of them are sent.** All 62 definitions are ~99 KB / ~33k tokens *per request*, and the agent loop re-sends them every round, so `initial_tool_defs(allow_writes, disabled)` sends the **core** group (~6.5k) plus one meta-tool, `ENABLE_TOOLS` (`enable_tools`), whose description names the remaining tools by group without their schemas. `enable_tools_def` builds that menu (returns `None` when nothing is left to fetch, so an empty menu is never advertised) and `enable_groups(args, allow_writes, disabled, already)` answers a call with the definitions to append. `tool_defs_for(allow_writes, disabled)` is the full pool both draw from: minus `WRITE_TOOL_NAMES` when the profile is read-only, minus `AppSettings.chat_disabled_tools`.
- `tool_groups.rs` - the catalogue: every tool's `ToolGroup` (Core / Quality / Compare / Combine / Reshape / Databases / Cloud / Write) and a one-line English `when` for the settings tooltip, plus `approx_tokens` (bytes of description + schema / 3). `every_tool_is_catalogued` pins it against `define_chat_tools!`; `the_core_payload_stays_small` fails if the first request grows past 10k tokens or stops being less than half the full set. `publish_to_settings()` (called once from `main.rs` before any UI) hands the list to `octa::ui::settings::chat_tools`, the library-side registry the Settings list reads - the tools live in the binary and the dialog in the library, so that `OnceLock` is the seam.
- `providers/` - one file per backend (`anthropic`, `openai`, `openai_compat`/`ollama`, `gemini`) behind `trait ChatProvider`. **OpenAI proper streams via the Responses API** (`openai_responses.rs`, `/v1/responses`): gpt-5.x 400s on `reasoning_effort` + function tools at chat/completions. `build_responses_body` sends `store:false` + (with reasoning) `include:["reasoning.encrypted_content"]`, FLAT tools `{type:"function",name,...,strict:false}` (strict must be explicit false - Responses defaults it on and schemars schemas do not satisfy it), `instructions` = system, `max_output_tokens`; reasoning = effort **word** (numeric -> local error), temperature OMITTED while reasoning is set. Reasoning items stream back as `ChatEvent::ProviderData` -> `ContentBlock::ProviderData{provider,data}` and are replayed verbatim before their turn's `function_call` items (gpt-5.x rejects a replayed function_call without its paired reasoning item); other providers' wire mappers filter the variant out. `handle_event` is a pure per-SSE-event fn (no `[DONE]`; `response.output_item.done` carries complete function_call arguments so argument deltas are ignored). `agent.rs` accumulates an ordered `raw_blocks: Vec<ContentBlock>`; dispatch iterates ToolUse only. `openai.rs` keeps the chat/completions helpers for `openai_compat`/`ollama`. `ProviderConfig.max_tokens: Option<usize>` (None=omit; Anthropic substitutes a high value). `gemini.rs::to_gemini_schema` sanitises schemars JSON Schema to Gemini's OpenAPI subset (resolve `$ref`, `Option`/`anyOf`->`nullable`, drop `additionalProperties`/`$schema`/`$defs`/`default`/`title`) else Gemini 400s. `stream_sse` extracts `error.message` from non-2xx bodies. Ollama is first-class: keyless `ChatProviderKind::Ollama`, `chat_ollama_url`, `src/app/chat/ollama.rs` (`is_running`/`list_models` via `/api/tags`; `start_server` spawns `ollama serve` in its own process group via `pre_exec(setsid)` so `stop_child_group` kills server + `llama-server` child; needs the `libc` unix dep). Panel worker threads do the model dropdown + Refresh/Start/Stop + ~5s status poll; Octa-started server killed on `on_exit`. SSE over blocking `ureq` on a `std::thread`; `stream_sse` uses `into_reader()` (not `read_to_string`, which defeats streaming). Providers assemble tool calls fully before emitting `ChatEvent::ToolCall`.
- `session.rs` - `ChatSessionState` (messages, `streaming`, `running`/`cancel` `Arc<AtomicBool>`, error) behind `Arc<Mutex<..>>`.
- `agent.rs` - `spawn_turn` runs on a `std::thread` holding only a cloned `egui::Context` + `Arc<Mutex<state>>` + a moved `ToolContext` (never borrows `TabState`). Loops up to `chat_max_tool_iterations`: stream -> commit -> dispatch tool calls (capped by `truncate_for_model`, 100 KB) -> append -> repeat. `tools` is **mutable**: an `enable_tools` call is answered in the loop (not in `dispatch`, which cannot reach the turn's tool list) and its groups are appended for the rest of the turn. A round that only fetched tools does **not** spend an iteration - with the default of 3 one fetch would eat a third of the budget - bounded by `max_fetch_rounds` (= the number of groups) so a model that only ever fetches still terminates. A call to a tool that is not in the live list is refused with a message saying whether it is switched off in Settings or simply not loaded yet. Per-turn `cancel`/`running` are fresh `Arc`s installed by `send_chat_message`; `cancel_chat` flips cancel and clears state; the worker's finally only clears shared state when `Arc::ptr_eq` confirms it's still the active turn.
- `persist.rs` - one pretty JSON per session under `<config_dir>/chat_sessions/`; autosaved per turn (debounced) and on new/load.
- `audit.rs` - opt-in tool-call audit log (`chat_audit_log_enabled`, off by default): each tool call appends one JSON line (`AuditEntry`: tool, args/result bytes, duration, is_error, ts) to `<config_dir>/chat_audit/<session_id>.jsonl`. `TurnRequest.audit_session: Option<String>` (set in `send_chat_message` from the session id when enabled) gates recording in `agent.rs`'s dispatch loop. Startup size warning: `OctaApp::new` sums `audit::total_size_bytes()`, sets `status_message` when `> chat_audit_log_warn_bytes` (default 10 MB) and `chat_audit_log_warn_enabled`. i18n `chat.audit_*`, `settings_hint.chat_audit_*`.
- `secrets` - in the library at `src/ui/settings/secrets.rs` (re-exported `crate::app::chat::secrets`). Per-provider keys, precedence **env -> keyring -> plaintext settings.toml**; `set_api_key` reports keyring-vs-fallback, `storage_location` reports the source. **Linux keyring = freedesktop Secret Service**, pure-Rust zbus. `keyring = "4"` is a single plain dep (no per-OS `[target.'cfg(..)']` blocks): its default `v1` feature picks `zbus-secret-service-keyring-store` on Linux (declared upstream with `crypto-rust`, so no libdbus and no OpenSSL), `apple-native` on macOS and `windows-native` on Windows, and `v1::Entry::new` registers the store itself on first call.

**Model profiles** (`src/ui/settings/chat_profiles.rs`, library-side since `AppSettings` is): `ChatModelProfile { id, name, description, kind, model, temperature, reasoning, base_url, use_own_key, allow_writes }` - an arbitrary `Vec` of named provider+model+params setups, several per provider allowed. **`allow_writes` (default false) REPLACES the global `write_protection` for the chat surface** (that switch keeps governing GUI file saves + the MCP startup default): `send_chat_message` passes it into `build_tool_context` (`allow_existing_writes`/`allow_schema_changes`/`read_only: !allow`) and `tools::tool_defs_for(allow, disabled)` (filters `WRITE_TOOL_NAMES` out of the advertised list; `dispatch` also refuses them on a `read_only` ctx, and `run_sql write_to` gates itself - that also closed the `--mcp-read-only` hole). The legacy-migration seed inherits `!write_protection`; profiles created later default read-only. The edit drain gate is `is_readonly() || !active_profile(..).allow_writes`. `build_system_prompt(tab_summaries, allow_writes, has_tool_menu)` adds a line telling the model that more tools exist behind `enable_tools` (only when the menu is actually sent), and swaps the write-tool guidance for an explicit READ-ONLY paragraph when writes are off (else the model speculates about "missing tool bindings" instead of naming the profile switch). `AppSettings.chat_profiles` + `chat_active_profile` (the id). `ensure_profiles(&mut settings)` runs in `AppSettings::load` (wrapping `load_raw`, so *every* path incl. parse-failure gets one) and on Settings-apply: seeds one profile from the legacy `chat_provider`/`chat_models`/`chat_temperature`/`chat_base_url`/`chat_ollama_url` fields (which stay as migration source + fallback) and re-points a dangling active id. `active_profile(&settings)` is the accessor. `id` is minted once via `fresh_id` and frozen (it names the keyring entry). Panel header = one profile dropdown (+ **Profiles...** -> Settings); Ollama keeps its server controls + discovered-model list in the panel, writing the pick back into the active profile (`set_active_profile_model`). The **Ollama server URL stays global** (the probe/start/stop target); a profile's `base_url` overrides it per request.

**Prompt caching (Anthropic)**: `build_body` sends `system` as a one-element block array carrying `cache_control: ephemeral`, and puts a second marker on the last message's last block. Anthropic hashes the prefix in the order tools -> system -> messages, so the marker on `system` covers the whole tool payload (the part that repeats unchanged every round) and the rolling one covers the conversation. Two of the allowed four. `message_start` is where the input token count comes from at all, and it sums `input_tokens` + `cache_creation_input_tokens` + `cache_read_input_tokens` so the meter keeps meaning "tokens sent". OpenAI and Gemini cache long prompts server-side with no request field, so nothing is sent for them.

**Thinking/reasoning**: `ProviderConfig.reasoning: Option<String>` (free text, empty = omit). OpenAI -> Responses `reasoning.effort` (word; numeric -> local error; temperature omitted while set); compat/Ollama -> `reasoning_effort` via the shared `build_body`; `anthropic.rs` -> `parse_thinking_budget` (numeric token budget; a word like `high` is a **local error** since Anthropic has no effort field) then `thinking.budget_tokens` + forces `temperature: 1` + lifts `max_tokens` above the budget (both API requirements) — `build_body` therefore returns `Result<Value, String>` and `stream_turn` `?`s it; `gemini.rs` -> numeric `thinkingConfig.thinkingBudget`.

**Keys** (`src/ui/settings/secrets.rs`) are now **id-based**: `get_key_for/set_key_for/delete_key_for/key_storage_for(key_id, env_var, ..)`. Two id spaces: provider (`kind.id()`, shared by every profile of that provider, env-var backed) and profile (`profile_key_id(id)` = **`profile.<id>`** — namespaced so a profile named "Anthropic" can't clobber the shared `anthropic` key; no env var). `get_api_key`/`set_api_key`/... and `get_profile_key`/`set_profile_key`/... are thin wrappers. A profile resolves its key via `chat_panel::profile_api_key` (own key iff `use_own_key`, else shared).

Settings live in the **main Settings dialog** (`src/ui/settings/dialog.rs`, "Chat / Assistant" `CollapsingHeader`); the panel's Settings button opens it via `settings_dialog.focus_chat_section` (+ one-shot `focus_chat_profiles`). The big sections use nested sub-`CollapsingHeader`s to separate per-instance from global config: Chat = "Model profiles" / "Global options" (`chat_global_options_grid`) / "API keys" (`chat_api_keys_body`), Databases + Cloud = connection list up front with the add/edit form behind a `settings.sub_conn_form` sub-header `.open(Some(true))`-forced while a row is being edited (cloud also via one-shot `focus_cloud_form` from the sidebar "+ Add"). The profile list + add/edit form is `src/ui/settings/dialog/chat_section.rs` (`chat_profiles_section`), backed by `chat_profile_form_*` buffers on `SettingsDialog`. `chat_*` fields in `src/ui/settings/mod.rs`: `chat_profiles`, `chat_active_profile`, legacy `chat_provider`, `chat_models: BTreeMap` per-provider, `chat_base_url`, `chat_ollama_url`, `chat_panel_position`, `chat_temperature` (default **0.0**), `chat_max_tool_iterations`, `chat_max_tokens` (default 16384) + `chat_max_tokens_unlimited`, `chat_export_dir` (default ~/Downloads), `chat_disabled_tools: Vec<String>` (the **off** list, so a tool added later defaults on), `chat_api_keys: BTreeMap`. Numeric settings use comma-tolerant text buffers. Chat tool context caps: `chat_result_row_limit` rows (default 200, user-configurable in Settings; `chat_result_row_limit_unlimited` checkbox -> `ToolContext.default_row_limit = None`, mirrors `chat_max_tokens`/`_unlimited`), 4 KiB/cell (`CHAT_CELL_CAP`). `table_to_json` adds a `note` to truncated results telling the model to write the full result to a file/tab and not to add a SQL `LIMIT`; the system prompt reinforces it. Chat UI strings under `[chat]` in every locale. The **Clear API key** button arms a confirmation (`chat_key_clear_confirm: Option<ChatProviderKind>`) — a second explicit click calls `secrets::delete_api_key`.

**Provider/model presets** are a hand-editable runtime `models.toml` beside `settings.toml` (`src/ui/settings/chat_models.rs`): `preset_models(kind)` / `default_model(kind)` read it, seeded from the `ChatProviderKind` consts and auto-written on first run; `reload()` re-reads (wired to a Settings "Reload models.toml" button). Missing/empty entries fall back to the built-in consts.

**Report AI content** (`src/app/dialogs/ai_report.rs`, `OctaApp.show_ai_report_dialog`): a Microsoft Store certification requirement, not a product idea — a product that *presents* generative-AI output must offer an in-product way to report it, and the Assistant panel renders model text even though Octa ships no model and runs no inference. Reachable twice: a **Report** button in the panel header and **Help -> Report AI content...** (`ToolbarAction.show_ai_report`) for when the panel is closed. Since the user brings the key or runs Ollama, a complaint about what a model *wrote* is only actionable by whoever serves it, so the dialog routes content reports outward via `ChatProviderKind::report_url()` (`None` for Ollama and OpenAI-compatible: no fixed page exists, so the dialog names the local model or the configured endpoint in prose instead) and keeps a second, always-present button for the part Octa does own, its own bugs on GitHub. `report_url` links are static and drift; re-check them before a submission. Rationale + the resubmission checklist in `windows/STORE_SETUP.md`.

Adding a provider: drop `src/app/chat/providers/<name>.rs` impl `ChatProvider`, add a `ChatProviderKind` variant + `make_provider` arm + a `report_url` arm. Adding a tool: free once the MCP tool has `run` + `DESCRIPTION` and is in `define_chat_tools!`.

## Plain-language entry points

- **Plain-language filter ("Ask")**: the search bar's Ask toggle retargets the search box (placeholder, width, focus) and sends the sentence to a chat profile via `chat/ask_filter.rs` (**one request, no tools, no agent loop**, so a search box can never become an autonomous session). While Ask is on, typing does **not** filter, or a half-written question empties the table. The reply is parsed into `AskResult { predicates, values, sort }`; failures apply **nothing**. Needed one new filter type: `column_filters` is a value allow-set and cannot express `amount > 1000`, so `src/data/predicate_filter.rs` + `TabState.predicate_filters` evaluate comparisons in `recompute_filter`, delegating every comparison to `conditional_format::rule_matches` (one comparison engine). Applied conditions show as removable chips above the table. Worker + `ask_filter_job` slot drained in the update loop; status bar shows `search.ask_running`.
- **Plain-language query ("Ask SQL")**: the SQL panel header's Ask box, a direct sibling of the search bar's. `src/app/chat/ask_sql.rs` is pure (`build_prompt`/`parse_reply`/`splice_at`/`ask`) and **one request, no tools, no agent loop**, same reason. The answer is **spliced into the editor at the cursor** (`splice_at`, byte offset captured at Save time from `TextEdit::load_state`, clamped to a char boundary) and **never run** - the user reads it and presses Run. `parse_reply` refuses anything that is not a single SELECT: a quote-aware semicolon scan (`split_points_outside_literals`, `''` = escaped, so `'a;b'` stays data) allows one trailing `;` and nothing after it, and the leading verb must be SELECT or WITH. Every failure applies nothing rather than half a query. On a db-origin tab in server mode the prompt names the real `schema.table` and that engine's dialect (`DbEngine::label()`), else `data`/DuckDB. **That same case also grounds the model in the server's declared foreign keys**: `ask_sql_job` runs `db::relationships::scan` on the tab's schema through `db_conn_cache` (two catalog queries, no table data) inside the worker, and `ask_sql::related_tables_block` turns the result into prompt text - the tables one hop out, their column names, and the key pair each join uses, capped at 8 tables / 40 columns (token budget, not correctness). `build_prompt` takes it as a sixth argument and, when it is non-empty, swaps `- Refer to the table only as X` for four rules: exact names, **join only on a listed pair**, prefer the base table alone, and do not aggregate a base-table column through a join that multiplies rows (the fan-out trap). Gated three ways, each falling back to the old single-table prompt: server mode only (a local DuckDB query has no neighbours to join), a non-empty schema (`scan` addresses everything as `schema.table`), and `DbEngine::has_foreign_keys()` (`scan` reads every column *before* it discovers ClickHouse/Trino/Athena have no keys, so an ungated call sweeps the catalog for nothing on every question). A failed scan logs `tracing::warn!` and asks anyway. A cross-schema parent comes back without columns (the key query filters on the child's schema, the column query on its own) and is listed as `(columns not read)` rather than with an empty list that would invite invented names. Worker + `ask_sql_job` slot drained in the update loop, reusing `search.ask_running` for the spinner. **`ask()` takes the already-built prompt (5 args), not the table facts (8)** - eight trips `clippy::too_many_arguments` and the no-`#[allow]` rule forbids the escape hatch. `SqlViewContext.chat_profile_available` is how the view layer knows to grey the box without reading settings. i18n `sql.ask*` (6 keys).
