# i18n

Hand-rolled `src/i18n.rs` (spans the lib/bin split): `t(key)` + `set_language(code)`, TOML catalogs embedded compressed from `locales/*.toml` by `build.rs` (2026-11-04, saves 8.5 MB; `catalog_of` unpacks and parses a language on first use, so tests must not walk the global language through all of them: other tests running in parallel read it) (**35 files total**: English master + 34 langs: de/es/ca/fr/it/nl/pt-pt/pt-br/pl/sv/da/nb/fi/tr/id/vi/ro/hu/cs + el/ru/ja/ko/zh-hans/zh-hant + uk/bg/sr-cyrl/hr/sl/sk + lt/lv/et). Roboto-Medium/Bold cover Latin+Greek+Cyrillic; the bundled NotoSansCJK-subset covers CJK/kana/hangul, Traditional characters included (so el/ru/ja/ko/zh-hans/zh-hant all render). `apply_fonts` also appends Roboto to the Monospace fallback so Greek/Cyrillic render in the SQL editor. `set_language` runs at `OctaApp::new` and on Settings apply (live). `every_language_covers_every_english_key` enforces key parity; `t()` falls back to English for any missing key. String migration is **incremental** — add a key to *every* locale then call `t()`. Arabic/Hebrew deferred (need RTL layout work).

**Variant locales, added 2026-10-31.** The code is the file name and the `LANGUAGES` id, and it is the Store's tag too, English (`en`, Store `en-us`) being the one exception (renamed 2026-11-06 from `pt`, `pt-BR`, `zh`, `zh-TW`, `sr`, `no`). `no`, `pt`, `sr` and `zh` shipped, so `i18n::current_code` maps them when `settings.toml` is read; a new rename of a shipped code needs a line there. `pt-pt` is **European** (informal `tu`, AO90: ficheiro, guardar, separador, ecrã, Definições, ligação) and `pt-br` **Brazilian** (`você`, which is the informal form there: arquivo, salvar, aba, tela, Configurações, conexão); the old `pt` mixed both, which is why it was rewritten. `zh-hant` is **Taiwan** wording despite its script-only name, and Taiwan swaps the table words: **列 = row, 欄 = column**, the opposite of `zh-hans` (行 = row, 列 = column), while a line of text stays 行. A new zh-hant string is therefore never a plain character conversion of the zh-hans one. `ca` is informal `tu` with Softcatalà terms (desa, pestanya, fitxer, Paràmetres; join = combinació, union = unió); the middle dot in `cel·la` is a letter, Roboto has it. Key names (Enter, Shift, Ctrl) stay as on the keyboard in every locale.

`every_language_covers_every_english_key` checks only that a key *exists*, which left two traps that both hit in practice: a whole section could ship untranslated and stay green (the entire `[union_tree]` block did, in all 31 locales), and nothing enforced a locale's script (`sr-cyrl.toml` is **Cyrillic** but once held 168 Latin strings, many ASCII-stripped past mechanical repair - a bare `c` is c, ch or ch depending on the word). Both now have their own test:

- **`non_latin_locales_are_written_in_their_own_script`** - a value in ru/uk/bg/sr-cyrl/el/ja/ko/zh-hans/zh-hant containing a Latin *word* (3+ letters) and no character of its own script fails, unless its letters match the English value, which is how product names (`JSON`, `Parquet`, `AWS IAM (RDS)`) stay Latin without an allowlist. It found and fixed **426 transliterated values** across seven locales on 2026-08-18.
- **`locales_do_not_carry_untranslated_english_sentences`** - a value identical to English with 3+ words fails. Single words are ignored (format and engine names are identical everywhere by design); `UNTRANSLATABLE_PHRASES` exempts the four real multi-word product terms.

Writing a locale in ASCII is a corruption, not a safety measure: the "ASCII only" rule for UI strings covers typographic punctuation (em-dashes, ellipsis characters, arrows) that egui's bundled font cannot draw, never alphabets. Roboto covers Latin/Greek/Cyrillic and the bundled NotoSansCJK subset covers CJK.
